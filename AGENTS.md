# AGENTS.md

- Any column that points a record at a person (assignee, leader, task owner) must have a BEFORE INSERT/UPDATE trigger checking that person belongs to the row's tenant (use `public.person_in_tenant` for user ids, `members.tenant_id` for member ids). Why: RLS alone doesn't stop an admin from linking another church's person, which leaks data via notifications.
- Account-wide admin actions (disable user, reset 2FA) by a non-super-admin must refuse targets who belong to any other tenant. Why: these actions affect every church the person is in.
- Settings that send member data to an admin-supplied URL (custom SMS/voice providers) may only be written by super-admins (DB trigger stamps `updated_by`), and edge functions must re-check `updated_by` is a super-admin before use. Why: prevents SSRF and data exfiltration by tenant admins.
- Any SECURITY DEFINER permission helper that takes a `_user_id` must begin with `public.rpc_probe_blocked('<fn_name>', _user_id)` and return false/0 when it's true. Why: stops signed-in users calling the helper directly to learn other people's roles, while RLS policies and triggers can still check other people.
- Edge functions that send assignment notices (text/email/bell) must skip repeats via `_shared/notice-dedupe.ts`. Why: re-assigning a record must not let someone spam the assignee.
- Texts sent by signed-in users must pass `smsContentProblem` in `_shared/sender-guard.ts`. Texts written earlier and sent later (scheduled texts, scheduled follow-ups) must pass `scheduledSmsContentProblem`, which judges by the author's role. It allows links from church admins only, and blocks shortened or number-only links and requests for passwords, codes or bank details. Why: stops a church login being used to phish its own members.
- `admin-create-user` must not reuse an existing account unless that person already belongs to the caller's church, and must never overwrite an existing profile. Why: other people join through an invitation they accept.
- Member-facing tables get a RESTRICTIVE SELECT policy `NOT tenant_is_suspended(tenant_id) OR is_admin OR super_admin`; Children Church check-in is exempt. Why: a suspended church loses member access, but children must always be collectable safely.
- Any `.ilike()` on a value a person typed (emails, names) must pass it through `escapeLike` (`_shared/like-escape.ts` in functions, `src/lib/like-escape.js` in the app). Why: unescaped `%`/`_` turn an email into a pattern that can match, claim or message someone else's record.
- Stripe subscription/top-up state is applied only through `_shared/stripe-sync.ts` (webhook, `verify-tenant-subscription` on the billing page, daily `sync-stripe-subscriptions` cron) and `tenant_payments.reference` is unique for Stripe rows. Why: webhooks can be missing or late, so every path must reach the same result without double-recording.
- Edge functions that send texts, emails or calls (live, scheduled or automatic) must refuse suspended churches (`tenantSuspended` in `_shared/sender-guard.ts`, super-admins excepted) and cap non-admin senders per 24 hours (`NON_ADMIN_DAILY_SMS_LIMIT`, `NON_ADMIN_DAILY_CALL_LIMIT`). Why: the app's suspension screen and quotas can be skipped by calling the function directly, and suspended churches must stop running up costs.
- Only the main parent or a church admin may change who the main parent is (children, teens, preteens triggers), edit the authorised pickup adults list, or delete/archive a child; one-time pickup codes also allow guardians the main parent listed as "Parent". Why: other authorised adults must not be able to promote themselves, add more people who can collect a child, or remove the child's record.
- People-written texts must not reach the same number twice in 24 hours with identical wording (`phonesAlreadySentMessage`) nor more than 5 times in 24 hours with any wording (super-admins exempt), and church emails can't be repeated by the same sender within 24 hours; non-admins have a daily email cap (`NON_ADMIN_DAILY_EMAIL_LIMIT`). Why: stops a church login being used to blast members.
- Admin-written automatic messages (birthday greetings) are only sent after `safeTemplate`-style checks (length, plain text, on-topic, content rules), falling back to the built-in wording; signed-in "test" sends go only to the caller. Why: stored templates reach every member without a human pressing send.
- Phone-call billing is per started minute: `call_log_meter_minutes` always derives `billable_minutes` from `duration_seconds` (supplied values ignored, never re-billed; `call_log` is written only by server code) and deducts minutes over the church's monthly allowance from `call_minutes_balance`; `make-call` refuses calls once allowance and balance are used up (0 allowance = unlimited), and only super-admins may change call and SMS/WhatsApp billing columns (limits, balances, price overrides, cycle start) via `tenants_guard_call_billing`; SECURITY DEFINER functions and service-role code still update them. Why: churches can't raise their own quotas, credit themselves or run up costs.
- Picture/flyer texts (MMS) count as 3 text units per person (server MMS_UNITS, client sms-coverage MMS_UNITS); text allowance sums sms_log.units via sms_units_used. Why: picture texts cost carriers more.
- Removing a person from a church (membership or member row) must delete their non-super-admin roles and unit leader assignments in that tenant (trigger revoke_tenant_roles_on_removal). Why: removed admins must not keep powers.
- Member-only rows and files (teen/preteen records, trivia, Bible School feedback, unit join requests, exam statements, certificates) carry a RESTRICTIVE policy requiring current `tenant_memberships` (or admin/super-admin). Why: a member row alone outlives removal from the church.
- The 5-texts-per-person-per-day cap also applies to scheduled texts (judged by `author_id`), and church email alerts cap each person at 3 per 24 hours (super-admins exempt). Why: delayed or bulk sends must not bypass the anti-bombarding rules.
- Only church admins, super-admins or the member themselves may change `members.email`, `phone` or `emergency_contact_phone` (triggers `members_guard_email_change`, `members_guard_phone_change`; clearing a number is allowed); contact details a non-admin types when adding a member are flagged `email_added_by_leader` / `phone_added_by_leader`, and non-admin texts, calls, alert emails and non-admin-written scheduled follow-ups skip flagged details. Why: stops a leader pointing a member row at an outside address or number and using the church to contact it.
- Sign-up must not link a member record or apply an invitation's admin/owner level until the email is confirmed (`handle_new_user` checks `email_confirmed_at`; `handle_user_email_confirmed` finishes the job on confirmation). Why: otherwise anyone can register someone else's address and take over their member record.
- Only church owners or super-admins may create or change invitations with the owner/admin level (trigger `tenant_invitations_guard_role`). Why: a church admin could otherwise insert an owner invitation for themselves directly.
- Certificate and statement emails must not contain open storage download links; link to the signed-in page (profile, exam results) instead, and keep any file link short-lived. Why: emailed links work for anyone who has them, even after the person leaves the church.
